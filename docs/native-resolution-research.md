# 原生分辨率切换与拍照坐标

## 已确认的问题

0.1.21 保留 2429×1518 输出缓冲，旧 Vulkan 场景链可改到 2240×1400，照片正常，但照片像素不能随自定义场景尺寸提高。

随后用户要求输出和照片都跟随自定义尺寸。0.1.22 只读追踪确认，游戏相机使用 Texture2D.ReadPixels；未进入原生 CaptureScreenshotAsTexture。原生 ReadPixels 调用者为 `0x4aa4020`。

0.1.23 在 ReadPixels 前调用原生 Texture2D.Internal_ResizeWH，再调整 Rect，成功保存 2240×1400 PNG；但用户发现内容向下移动、顶部出现拉伸异常。因此该版本**未修复内容兼容性**。文件尺寸正确、最后一次 buffer readback 不越界，仍不足以证明中间坐标与内容正确。怀疑旧逻辑高度仍参与底左/顶左坐标转换；这是假设，尚未完成逐次 Vulkan blit 验证。没有把增加固定 Y 偏移当作通用修复。

## PC 静态对照

只读分析用户提供的旧版 `E:\Game\Genshin Impact Game\YuanShen.exe`，未启动旧游戏，未修改 E 盘文件。PE image base 为 `0x140000000`，下表为 RVA：

| 入口/区域 | RVA | 静态证据 |
|---|---|---|
| 分辨率请求 | `0x178dd00` | 将宽、高、全屏、刷新率存入对象 `+8/+c/+10/+14`，立即返回 |
| 消费请求 | `0x178dd20` | 检查上述字段的 -1 默认值；补充当前值；调用 vtable `+18` 应用；重置请求字段为 -1 |
| Windows 屏幕管理器 vtable | `0x21d06a0` | 请求槽 `+8` 指向 `0x178dd00`，更新槽 `+10` 指向 `0xac4230`，应用槽 `+18` 指向 `0xac3c10` |
| 当前宽/高 getter | `0xac4970` / `0xac4980` | 位于该 vtable 的 `+d8/+e0` |
| 窗口/显示模式相关代码 | `0xaf7fa0` 周边 | 可见 GetClientRect、AdjustWindowRectEx、SetWindowPos，以及 ChangeDisplaySettingsW 的导入调用 |

这些证据确认 PC 原生请求/更新/应用的结构；没有声称已完整恢复该旧版游戏设置页到所有显示驱动资源的调用链。MSVC 与 Android Itanium ABI 的析构槽数量不同，不能直接照搬 vtable 索引。

本地静态产物：`build/pc-resolution-survey.json`、`pc-resolution-import-xrefs.json`、`pc-screen-vtables.json`、`pc-screen-request-apply-confirmed.txt`。最初 .pdata 解析得到的函数范围无效，后续只以直接反汇编区域及实际函数指针关系为证，不依赖该范围推断。

## 安卓对应入口

| 入口 | RVA | 行为 |
|---|---|---|
| Screen.SetResolution（4 参数） | `0x80ec67c` | 跳转到原生 binding |
| 原生 binding | `0x4a8f998` | 取 ScreenManager，调用 vtable `+10` |
| 分辨率请求 | `0x56ec12c` | 与 PC 一样写 `+8/+c/+10/+14` |
| 消费请求 | `0x56ec1a0` | 读取请求、调用 vtable `+20`、重置请求 |
| 安卓应用分辨率 | `0x50b7120` | 写逻辑宽高 `+6c/+70`，记录旧宽高、遍历并通知渲染对象，然后执行平台更新 |

0.1.24 增加研究路径 3：在游戏 Tick 提交一次原生尺寸请求；对游戏随后经同一 binding 发出的请求保持已冻结的目标宽高，保留原请求的全屏、刷新率参数。几何目标选择改为相对于原生更新后的输出尺寸判断，避免逻辑输出变小后漏掉较小的主场景目标。其余 viewport/framebuffer 配套调整仍沿用已测量的 Vulkan 路径。

该原生 binding 纳入当前版本代码指纹校验，入口安装失败只影响图形功能，不影响键鼠。请求排队与实际尺寸应用不是同一件事，必须读回逻辑宽高并检查成功提交的绘制链。

0.1.24 初次实机观测到用户设置 1920×1200 时，ScreenManager 逻辑尺寸与 swapchain 同为 1920×1200；当时处于资源校验界面，未将加载界面采样当作大世界验证。用户随后确认该配置拍照正常。

0.1.25 后续验证了用户已保存的 3200×2000：ScreenManager 与输出缓冲为 3200×2000；大世界连续三帧的主几何、HDR 全屏处理、最终场景合成与输出均为该尺寸，无命令缺失或超限。保存的 `20261115210157.png` 为 3200×2000，读回同尺寸且越界计数为 0；用户确认“镜头正常，3200×2000 照片也正常”。保留用户当前的 90 FPS 上限、80% 关联距离、关闭特效增强。原生路径 3 已成为无研究配置时的默认路径。

原生路径的预期是让拍照自身看到正确逻辑尺寸，从而不需要旧的 ReadPixels Rect 改写。0.1.23 的改写目前仅限研究路径 1；路径 3 的 ReadPixels 保持原调用。
