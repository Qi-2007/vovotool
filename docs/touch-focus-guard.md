# 触屏激活 PC 游戏窗口

## 触发条件

用户在多窗口环境报告：启用 PC 界面时，从其他窗口用触屏直接点击游戏画面获得焦点，会出现秘境重新加载或主世界摄像机定住。点击标题栏、使用鼠标、保持瞄准状态、使用原生触屏 UI 时均未出现同样现象。

这些差异指向用于激活窗口的首个触屏事件，但不能单凭现象认定为进程崩溃或某个原生方法的错误。

## Java 事件保护

- 在原神主 Activity 实际继承的 `onWindowFocusChanged` 入口记录焦点变化，并同步清理原生捕获与按键状态。原 Activity 的焦点回调照常执行。
- 在实际继承的 `dispatchTouchEvent` 入口检查触屏来源。仅当模块已应用 PC 键鼠模式，且该 Down 发生于失焦状态或刚获得焦点的 180ms 窗口内，才把该手势用作激活窗口。
- 一旦接住 Down，就消费同一手势直至 Up / Cancel，避免遗漏 Down 后仍将 Move / Up 送入 Unity。
- 鼠标和触控板不走这个分支；窗口稳定获得焦点后，普通触屏事件继续传入游戏。模块主开关关闭或原生触屏模式时不开始拦截新手势。

## 原生模式保护

本版本 `MHCNPJOGAGH.IGKCDAAKAOI`（RVA `0xe1cb1fc`）包含完整的输入/UI 模式切换：清理界面集合、更新 UI 设备、重置相机相关组件、发送模式通知等。该函数签名为 `bool(self, uiDevice, inputMode, MethodInfo*)`，代码指纹已加入构建 profile。

模式保护在模块启用、PC UI 设备为 1、键鼠模式为 2、对象身份匹配时阻止自动切换到其他配置，并在重新获得焦点的 400ms 内避免重复完整重建。UI 设备 setter 另行阻止切回非 PC 设备。模块首次应用和关闭后的恢复通过原 setter 执行，不受保护阻挡。

这是一层防止自动重建的保护。本次成功验证中没有看到该切换函数的请求，不能据此断言它就是原 bug 的底层根因。

## 验证记录

0.1.6 构建、v2/v3 APK 签名校验、覆盖安装成功。用户在未瞄准状态测试触屏点回，并测试鼠标点回，确认“触屏点回已正常，鼠标也正常”。整个验证由 LSPosed 加载，游戏进程没有 Frida 映射。

验证快照中，游戏 PID 保持为 6467，`stage=2`、输入模式 2；失焦 11 次、获得焦点 12 次；接收 62 个触屏 Down，其中 9 个手势的 18 个事件用于激活窗口。PC 输入仅应用一次，原生 UI/模式切换请求和保护拦截次数均为 0。

数据保存在 `build/verified-focus-0.1.6.json`。只验证了用户报告的实测流程，未穷尽所有多窗口系统或所有界面。

## 诊断

`diagnostics` 新增两个独立数组，原有键鼠 `state` 和 `uidState` 不变：

- `focusState`：PC 应用次数、UI 设备请求数、完整模式切换请求数、阻止 UI 设备次数、阻止完整切换次数、最近请求 UI 设备、最近请求输入模式、最近模式切换调用者 RVA、保护开关。
- `windowState`：失焦数、获焦数、触屏 Down 数、消费的激活手势数、消费事件数、当前窗口焦点、是否正在消费手势、保护开关、最近触屏来源、最近触屏 action。

根或模块自身可用配置 Provider 的 `set_focus_guard` 调试方法临时切换该保护；普通应用和游戏不能调用该调试设置。日常使用默认开启，不需要额外配置。
