# 触屏纵向输入及进入场景后启用 PC UI

## 实测证据

完整 PC 模式中，普通镜头用手指上下滑动很慢，瞄准正常。Java 触屏入口原先只处理首次点回窗口的保护，没有触控板倍率转换。普通镜头和瞄准分别使用 `DBOLJJLIEJI`、`HDNAMHCOJHK` 控制器。

同一进程、大世界普通镜头下，用 Android `input -d 2 swipe` 产生 400 像素位移，并读取普通控制器的球面角度：横向约 38.8°，纵向约 0.72°。在 `MonoInputEasyTouch_H4` 的纵向基础参数上临时乘 150/34，用户仍认为偏慢；恢复后改为乘约 57.2958，用户确认速度合适。此倍率接近角度/弧度换算，但尚未定位到导致单位差异的唯一指令，不能据此宣称根因已证明。临时字段修改均只属于旧进程现场测试。

另一现场在移动 UI 进入大世界后才启用模块，设备字段为 1、输入模式字段为 2，光标仍为 1000。截图可见队伍键盘提示与移动端攻击按钮同时存在，Android 指针没有捕获。现有启用逻辑直接改设备、输入模式和 Rewired maps，未完整重建已经实例化的场景主页面。因此字段成功并不代表整个 PC 界面已完成切换。此状态的触屏表现不能作为完整 PC 路径的验证结果。

## 0.1.26 实现

- 挂接 `MonoInputEasyTouch_H4` 的原生旋转入口 `0xcc6f6c8`。只在模块已应用、输入模式 2、窗口有焦点、光标为 -1、近期收到真实 Android 触屏事件，且当前相机实际使用普通控制器时，对送入原函数的纵向参数应用实测补偿。横向、共享鼠标系数、保存的灵敏度和组件字段不修改。
- 瞄准及其他控制器、菜单、上述混合 UI、鼠标及触控板输入保持原路径。独立代码指纹不匹配时不安装本项 hook。
- 在已打开 `InLevelMainPage` 时主动启用模块，先调用游戏原生 `IGKCDAAKAOI(input, 1, 2)` 完成 UI/输入切换，再应用 PC 键鼠与模式保护。原生未接受时每秒最多重试一次，不先写入半套 PC 模式。启动早期接入继续保留原路径。
- 自动触屏切模式和点回窗口的保护继续存在；主动启用所需的原生重建与自动焦点切换分开处理。
- 诊断 `touchLookState=[安装状态,旋转入口调用数,触屏补偿次数]`；安装状态 1 为成功，-1 为代码不匹配，-2 为 hook 安装失败。

## 验证

独立 ARM64 `tests/touch_look_test.cpp` 已验证普通触屏补偿，以及瞄准、菜单/混合光标、无近期触屏、关闭、失焦、移动模式和其他对象的透传。APK 构建及 v2/v3 签名校验通过。

设备安装 `0.1.26` 后，以主开关关闭的移动 UI 进入大世界，再开启主开关：`state=[2,2,-1,1,...]`，PC 按键提示出现；Android `dumpsys input` 确认原神窗口 Pointer Capture Enabled。普通镜头受控触屏滑动使 `touchLookState` 从 `[1,0,0]` 变为 `[1,17,17]`；切换安柏瞄准后同样滑动，入口调用变为 35，补偿数仍为 17，确认瞄准透传。随后退出瞄准。记录见本地 `build/touch-native-hook-26.json`、`build/touch-aim-passthrough-26.json` 和 `build/activation-pc.png`。

用户实际检查普通触屏纵向、瞄准、鼠标/触控板及攻击按钮样式后回复“正常”。确认后未再次切换开关或重启。验证范围限于当前版本和上述场景；在其他菜单中启用时的完整 UI 重建尚未验证。
